# 기록 아키텍처

- 요구사항: HOME-01, PHOTO-01. 책임: 대상별 분석 기록 및 기준 버전 조회.
- 현재 상태: `FirestoreRecordsRepository`가 선택된 그룹별 기록을 보존하고 요청 ID를 문서 ID로 사용해 중복 저장을 멱등 처리한다. 분석 사진과 기준 사진은 Storage에 저장한다. Preview는 메모리 저장소를 사용한다.

## 흐름과 계층

화면은 사용자 입력을 BLoC/Cubit에 전달하고 로딩·성공·빈 상태·실패를 렌더링한다. 일회성 이동과 메시지는 지속 상태와 분리한다. Domain은 엔티티·유스케이스·저장소 계약을 소유하고, data는 DTO·데이터 소스·저장소 구현을 제공한다. 앱 조립 계층이 구현을 주입한다.

## 데이터와 연동

- 의존성: 분석 결과 저장소와 그룹 권한.
- JSON은 data 경계에서 DTO로 검증하고 도메인 모델로 변환한다. 공통 오류는 실패 타입으로 변환한다.
- 문서는 `groups/{groupId}/records/{requestId}`이며 관련 이미지들은 그룹 내 기준 대상과 기록 경로에 저장한다. Firestore/Storage 규칙에서 승인된 구성원 권한을 검증한다.
- 테스트에는 가짜 저장소와 고정 상태를 사용한다. 네트워크·플랫폼 플러그인을 Preview에서 호출하지 않는다.

## 검증 및 결정 대기

- 정상·빈 상태·실패·재시도와 권한 거부를 테스트한다. 입력·삭제·중복·그룹 격리는 해당 기능 구현 시 추가한다.
- 선행 결정: 보관·삭제 정책 및 시간대. 실제 연동 전에 계약과 수용 기준을 구체화한다.
- 설계 변경 시 PRD 요구사항과 상태·인터페이스·테스트를 함께 갱신한다.

## 기능별 설계 상세

- 화면 흐름: 대상 선택 → 기록 목록 → 기준과 후속 사진·결과 상세.
- 상태·계약: RecordsCubit: 대상별 조회 및 상세 조회; RecordsRepository: 그룹·대상별 기록 조회.
- 필수 테스트: 기준 버전·원본·수정값 일치, 그룹 간 격리, 중복 합산 방지.
- 목록과 상세는 기준 버전·선택 시각·분석 시각·사진·원본 결과와 사용자 확인 결과를 표시한다. 이 메모리 구현은 앱 종료 시 기록이 사라진다.
- Firebase 구성: `FirestoreRecordsRepository(firestore:, storage:)`; `RecordsCubit` 호출 시 반드시 인증된 활성 `groupId`를 전달한다. 대상별 기록을 조회한 뒤 분석 시각으로 정렬하므로 복합 인덱스가 필요하지 않다.

- 보호자 확인값과 메모 수정은 독립 입력 화면에서 수행한다. 원본 사진·모델 결과·분석 시각은 변경하지 않는다. Firestore 트랜잭션은 이전 확인값을 비교해 동시 수정 충돌 시 저장하지 않고 오류를 표시한다. 가족 전체 타임라인은 `listAll(groupId:)`로 조회한다.
